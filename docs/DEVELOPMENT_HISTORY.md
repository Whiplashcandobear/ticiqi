# 演讲提词器开发历程与问题复盘

## 1. 项目目标

项目围绕一个明确场景展开：演讲者需要使用手机录制英语演讲视频，同时在另一部手机上阅读台本。台本必须清晰、完整、可调整，并在真实语速发生变化时仍然可靠。

设计原则被固定为四点：

1. 录制时优先保证可读性，而不是堆叠复杂功能。
2. 长句不能被固定容器或底部控制栏裁掉。
3. 固定 WPM 必须始终可用，语音识别不能成为单点故障。
4. 用户台本和录音相关数据默认留在本机。

## 2. 版本化开发过程

### 阶段 A：MVP 与视觉方向

- 建立 Android Compose 工程和本地台本数据模型。
- 完成首页、编辑页、播放设置页、播放页和悬浮窗。
- 采用深色/浅色双主题、三种强调色、四档字号、倒计时和默认竖屏。
- 参考确认后的视觉方向，保持页面简洁、控件直接可操作。

### 阶段 B：文本排版稳定性

最早的问题是：复制自 Word 或其他编辑器的文本可能含有排版软件插入的硬换行。若直接按换行切分，原本完整的一句话会变成两个播放单元。

处理方式：

- 在解析层只把段落换行和句末边界当作结构信息。
- 句子内部的单个硬换行被合并为空格。
- 播放单元保留完整原句，显示层负责自然折行。
- 当前长句自动锚定到视口上方，避免尾部被底部控制栏遮挡。

结果是：排版可以换行，但语义句子不会被截断或错误拆分。

### 阶段 C：播放控制与横竖屏

实际使用中发现：

- 进度条只能显示，不能拖动。
- 横屏时按钮占用过多空间，遮挡当前句。
- 横屏分支遗漏了当前句高亮。
- 播放和暂停时都需要能拖动浏览全文。

处理方式：

- 增加进度比例到句子索引/句内进度的双向映射。
- 横屏使用紧凑控制栏，缩小暂停和从头按钮。
- 竖屏与横屏共用当前句渲染器和字符高亮渲染器。
- 使用可滚动的全文容器，播放状态不禁用用户浏览。

### 阶段 D：速度校准

固定 WPM 对不同演讲者并不完全准确。为此加入：

- 取台本前 60 个英文词作为校准片段。
- 用户按真实演讲方式朗读并计时。
- 根据词数和耗时计算 WPM，并按 5 WPM 取整。
- 播放中提供 −5 / +5 WPM 微调。

固定 WPM 仍然保留，适合不使用麦克风、环境嘈杂或需要严格控制总时长的场景。

### 阶段 E：实时语音跟随与混合回退

用户进一步提出：真实语速有时快于设定速度，有时慢于设定速度。最终方案不是强行让固定滚动速度猜测用户，而是增加可选的实时语音跟随：

- Android 设备端识别优先。
- 识别结果在当前句和后续有限窗口内进行标准化匹配。
- 使用滞后确认，避免单个公共词造成跳句。
- 识别有效时按句更新位置和字符进度。
- 连续约 2 秒没有有效识别时自动切换固定 WPM。
- 识别恢复后需要稳定结果才退出回退状态。
- 播放页和悬浮窗复用同一个纯 Kotlin 句级状态机。

该方案明确选择了可靠性优先：即使语音识别不可用，用户仍然可以完整完成演讲。

### 阶段 F：安全整理与重新上传

在推送到公开仓库前，执行了以下整理：

- 排除 `local.properties`、构建目录、APK、签名文件、密钥和环境变量文件。
- 扫描 API key、token、密码和私钥特征。
- 增加 `SECURITY.md`，说明本地存储、麦克风权限和系统识别服务边界。
- 增加 CHANGELOG、问题复盘和构建工作流。
- 保留可复现的 Gradle Wrapper 和测试代码。

## 4. 当前仍需真机确认的内容

- 不同品牌手机是否提供可用的设备端英语识别服务。
- 语音识别和相机同时使用时的麦克风资源竞争。
- Android 版本差异对悬浮窗前台服务和录音权限的影响。
- 长时间演讲时识别器自动重启的稳定性。

这些属于设备环境验证，不应被文档包装成已经在所有手机上验证通过。
